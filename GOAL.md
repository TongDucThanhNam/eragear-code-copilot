## Objective

Complete Supervisos as a production-grade, durable multi-agent orchestrator for
Eragear Code Copilot: one Supervisor AI must be able to turn one approved user
goal into a validated dependency graph, create and manage multiple independent
ACP-backed worker sessions, supervise their turns and permissions, safely
integrate their results, recover after restart, and expose the whole run in the
desktop UI.

“100% complete” for this goal means every Success Criterion below has current,
authoritative evidence. The existing single-session auto-continue loop, side
chat, Scope Resolution, and isolated Goal Mode tests are foundations only; they
do not by themselves satisfy the multi-session objective.

The implementation must preserve the Electron-first package boundaries:
runtime and business behavior belongs in `packages/runtime`, client contracts
belong in packages, and Electron main/preload remain lifecycle and native
integration shells.

## Feasibility Decision

This goal is feasible and hard.

The repository already provides most low-level seams needed by an orchestrator:

- `CreateSessionService` creates and persists a live ACP-backed session.
- `SendMessageService`, prompt lifecycle events, session stop/resume, and
  session queries provide the worker lifecycle primitives.
- `SupervisorLoopService` reviews a completed turn and can send a bounded
  follow-up to the same session.
- `SupervisorPermissionService` preserves allow-once selection, hard-deny
  rules, ownership checks, and fail-closed behavior.
- `BotsService` demonstrates durable run records, new-session execution,
  concurrency limits, queued retry, and lifecycle completion handling.
- `ScopeResolverService`, the AST import graph, worktree change collection,
  and Goal Mode gates provide scope and verification primitives.
- The desktop renderer already supports multiple workspace tabs and has a
  Supervisos side panel.

The missing work is not a small UI extension:

- No production service owns a parent run and a DAG of worker tasks.
- Supervisos does not currently create worker ACP sessions.
- Existing `SubagentInvocation` records are metadata inside one parent
  session; they do not create or supervise independent ACP sessions.
- The local `ForkSessionService` copies stored history into a stopped chat; it
  is not ACP `session/fork` and does not provision a live worker.
- `GoalModeController` is constructed with an in-memory repository and has no
  production caller for `startGoal`, `startPhaseAttempt`, or
  `handleLoopResult`.
- Runtime code defines the `goal_mode_audit` event shape, but current
  production Goal Mode code does not emit it.
- `initializeSupervisorEvents` ignores `automation` turns, so sessions
  launched by automation are not automatically reviewed by the current
  Supervisor loop.
- Multiple write-capable sessions pointed at the same project root would race
  and could overwrite user or peer changes. Safe isolation and integration are
  mandatory.

The implementation should deepen existing modules and ports. Do not build a
second ACP stack or hide orchestration inside renderer state.

### Product Definition

A Supervisos run is a project-scoped control-plane object. MiniMax-M3 may
propose a task graph and semantic decisions, but deterministic application
services own validation, state transitions, session creation, scheduling,
permission enforcement, workspace isolation, patch integration, retries,
budgets, and terminal status.

A worker is an independent ACP-backed chat session with its own `chatId` and,
when available, agent-side `sessionId`. Workers may use the same configured
agent implementation or different configured agents. The Supervisor model is
not allowed to invent commands, executable paths, credentials, or agent IDs.

### ACP Compatibility Findings

The official ACP v1 documentation defines each session as an independent
conversation with its own context, history, and state. `session/new`,
`session/prompt`, `session/cancel`, and session updates form the required
baseline. Session list is stable; load, resume, and close are capability-gated.
The installed SDK schema includes list, resume, close, and fork, but marks some
of those surfaces unstable because the installed SDK predates current
stabilization. The official `session/fork` page remains an RFD rather than a
required orchestration primitive.

Therefore:

- Fresh workers must use the required `session/new` path through the existing
  runtime session service.
- Local durable `chatId`/worker bindings are authoritative for orchestration.
- `session/list`, `session/load`, `session/resume`, and `session/close`
  may be used only after capability checks.
- ACP `session/fork` is optional and not required for completion.
- Do not upgrade the ACP SDK merely to claim orchestration. Upgrade only if a
  required stable capability cannot be implemented with the installed SDK, and
  add compatibility evidence first.

### Planning Contract

MiniMax-M3 returns a strict structured proposal containing tasks,
dependencies, roles, execution modes, candidate configured agent IDs, scope
intent, and verification requirements.

Deterministic validation must reject:

- Empty plans or plans above the configured task cap.
- Missing or duplicate task IDs.
- Cycles, self-dependencies, and references to unknown tasks.
- Dependency depth above the configured bound.
- Unknown roles or execution modes.
- Unknown/inactive agent IDs.
- Absolute paths, traversal paths, or files outside the project root.
- Write tasks with no scoped targets unless the run is paused for user review.
- Commands or executable paths proposed by the model.
- Plans requesting commit, push, deploy, credential access, destructive file
  operations, or permission bypass without explicit user authorization.

The planner may revise a graph only through a versioned replan transition.
Already integrated task outputs cannot silently disappear from a new graph.

### Worker Session Contract

- Add explicit internal prompt source `orchestrator`; do not overload normal
  user turns or globally enable Supervisor review for unrelated automation bots.
- Persist `runId -> taskId -> attemptId -> chatId -> agentSessionId` binding
  before or immediately after session creation through an idempotent
  reconciliation transition.
- Use `CreateSessionService`; do not directly spawn ACP processes from the
  orchestration module.
- Use `SendMessageService`; do not bypass prompt busy handling, message
  persistence, lifecycle notifications, or session locks.
- A worker prompt contains original intent, stable constraints, its task goal,
  compact dependency summaries, allowed files, verification commands, and
  output schema. It must not contain raw sibling transcripts or full raw diffs.
- The existing Supervisor loop may continue a worker within its task and
  attempt limits. Run-level transitions remain owned by the orchestrator.
- Terminal worker decisions publish or trigger a structured task-result
  collection path exactly once.

### Workspace Isolation and Integration

For Git-backed projects:

- Every write-capable worker uses its own detached temporary worktree rooted
  under runtime-controlled app data.
- A worker session's project root is the isolated worktree, so existing
  project-root sandboxing naturally confines it.
- Do not auto-commit, push, deploy, reset, stash, or switch the user's branch.
- Capture main-worktree HEAD, dirty paths, and target-path fingerprints before
  dispatch.
- If a task overlaps a pre-existing dirty user path, pause with
  `needs_user` before dispatch or integration.
- Collect binary-safe patch data plus created/deleted/renamed file manifests.
- Integrate only after scope, verification, deletion, destructive-action,
  conflict, and baseline-drift gates pass.
- Apply a validated patch to the user worktree without committing.
- If the user worktree changed on a touched path after dispatch, fail closed to
  `needs_user`; never overwrite the newer change.
- Always dispose or reconcile temporary worktrees after completion,
  cancellation, failure, and restart.

For non-Git projects:

- Read-only workers may run concurrently.
- Automatic parallel write integration is unsupported and must visibly fail
  closed to `needs_user`.
- The implementation must never silently fall back to multiple writers in the
  same directory.

### Result and Gate Contract

Each terminal attempt must record:

- Semantic terminal status and reason.
- Compact outcome summary.
- Files touched, created, deleted, and renamed.
- Verification commands with exit codes and bounded output summaries.
- Patch artifact reference and hash for write tasks.
- Tool failure summary and unresolved permissions.
- Agent and session identifiers.
- Timing and attempt count.

A task can become `completed` only when:

- Its worker is terminal with a successful semantic decision.
- Required verification evidence exists and passes.
- Scope and deletion gates pass.
- No unresolved permission or tool failure remains.
- Its patch is integrated or the task is explicitly read-only.

A run can become `completed` only when:

- Every required task is completed.
- No task is queued, running, reviewing, integrating, failed, or needs-user.
- The final aggregate verification commands pass in the user project root.
- The final summary references actual task results and evidence.

### Persistence and Recovery

Implement `SupervisorRunRepositoryPort` with a durable, versioned app-data
adapter. It must serialize transitions, write atomically, reject stale revision
updates, and survive runtime restart. Follow the repository's existing
persistence conventions; a versioned atomic file adapter patterned after
`BotFileRepository` is acceptable, as is a transactional SQLite adapter.
Behavioral evidence is authoritative, not the storage brand.

On runtime startup:

- Load non-terminal runs.
- Reconcile each worker binding with stored and live sessions.
- Resume/load only when the agent advertises the required ACP capability.
- If a worker cannot be resumed, mark the attempt `interrupted`, clean its
  resources, and retry only within the attempt budget.
- Recompute ready tasks from persisted dependency states.
- Never duplicate a prompt because the same completion or startup event was
  processed twice.
- Runs already paused or needs-user remain paused after restart.

### Goal Mode Unification

`SupervisorRunState` is the authoritative multi-session run aggregate.
Existing Goal Mode must take one of these explicit forms:

1. A sequential-plan facade over the new orchestrator, or
2. A gate/scope/prompt subsystem used by the orchestrator.

It must not remain an independently wired in-memory controller with no
production entrypoint. Existing `goal_mode_audit` compatibility may remain,
but new run/task events are the primary multi-session surface.

### Observability

Derive metrics from persisted tasks and attempts:

- Run/task completion and failure counts.
- Queue, execution, review, and integration duration.
- Active and peak worker concurrency.
- Attempts and continuation counts.
- Gate rejection reasons.
- Planner replan count.
- Per-agent success/failure and duration.
- Context/prompt sizes when available.
- Recovery and interrupted-attempt counts.

Do not store mutable aggregate metrics as a second source of truth.

## Out of Scope

- Distributed/cloud orchestration across multiple Eragear runtime hosts.
- One run spanning multiple project roots.
- Automatic parallel write integration for non-Git projects; it must fail
  visibly closed.
- Requiring or standardizing ACP `session/fork`.
- Replacing ACP with a proprietary agent-to-agent protocol.
- Automatic commits, pushes, pull requests, deployments, or branch changes.
- Training or fine-tuning MiniMax or worker models.
- A general agent marketplace or arbitrary downloaded executables.
- Full native/mobile orchestration UI parity; native contracts must remain
  compatible, while the operational Runs UI is desktop-first.
- Rebuilding the entire chat/session UI or design system.
